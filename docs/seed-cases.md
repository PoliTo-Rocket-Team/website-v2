# Seed cases

The dummy set that `pnpm db:seed` loads into a local database and into the one Neon branch every preview reads, named `preview` ([ADR 0016](../.decisions/0016-previews-read-their-own-seeded-branch.md)). This page lists every case the set holds and the board or issue that case exercises, so a reviewer knows where to look and a maintainer knows what a change to the seed may break.

## How the seed runs

- `pnpm db:seed` runs [db/seed.ts](../db/seed.ts). It checks the target first, then runs every module in [db/seed/registry.ts](../db/seed/registry.ts) in one transaction: each module's reset (last module first), then each module's insert (in order). Running it twice leaves the same rows, including columns a default or a trigger fills. It leaves the audit table `logs` empty.
- The seed sends each value the way drizzle maps it, as the app does: a json or jsonb value is encoded once, so an array is stored as an array ([db/seed/connection.ts](../db/seed/connection.ts)).
- `pnpm db:seed --check` runs the target check alone and writes nothing.
- The check reads `DATABASE_URL` and allows only these targets:
  - a local database (`localhost`, `127.x.x.x` or `::1`);
  - the shared Neon branch named `preview`, known by its compute endpoint `ep-floral-mouse-b2er5ebz` in the connection host (the direct host or the `-pooler` one), and only on a Vercel preview build (`VERCEL_ENV` is `preview`).
  The check reads the host alone. It calls no Neon API and needs no Neon key.
- It refuses everything else: a Vercel production build, any other Neon endpoint (production's among them), any host it cannot classify, and the `preview` branch's endpoint outside a preview build. No variable or flag turns a refusal into a pass. The rules, and the endpoint id, are in [lib/seed/target.ts](../lib/seed/target.ts). If the `preview` branch is ever recreated, its new endpoint id replaces that one constant.
- A preview build seeds the `preview` branch itself: `pnpm build` runs [db/preview-build.ts](../db/preview-build.ts) before `next build`. On a Vercel preview build given a `DATABASE_URL`, it checks the target, then, under a Postgres advisory lock so concurrent preview builds take turns, migrates it and seeds it only when it is empty (no `departments` row yet). It never resets it: a branch that already holds data is migrated and left as it was (issue #465). When it seeds, under the same lock it uploads two PDFs to the private Blob store, each unless it is already there, and writes nothing else to the store. The first is one shared sample PDF at `applications/seed-sample.pdf`, owned by nobody: every seeded application's motivation letter and every CV but one point at it, so the Applications panel's document cards open it (issue #406). The second is the applicant plain seat's own CV at `applications/seed-applicant-cv.pdf`, owned by that seat and sent as application 24's CV, so the apply form offers that seat a stored CV (issues #826, #833). A preview with no `BLOB_READ_WRITE_TOKEN` skips the uploads and says so in the build log. A production build given a database only migrates it, under its own advisory lock, and never seeds it ([ADR 0020](../.decisions/0020-production-builds-migrate.md), issue #874). Development builds, local builds and a build with no database skip it all. A refusal or failure fails the build.
- A preview build re-seeds the `preview` branch only when the owner asks, once per request ([Re-seed the preview branch](#re-seed-the-preview-branch)). It then empties every table of the `public` and `better_auth` schemas but `preview_reseeds`, those no seed module owns included (`logs`, sign-in sessions, `outreach_summit_versions`), and loads the dummy set, in one transaction ([lib/seed/reseed.ts](../lib/seed/reseed.ts)). It calls no Neon API and never resets the branch from its parent, which is production.
- The rules for agents ([ADR 0016](../.decisions/0016-previews-read-their-own-seeded-branch.md), amendment of 2026-10-24): agents may write to the `preview` branch through a preview deployment to set up and check a state; it is re-seeded on demand, never on every build; production is never written to or seeded by agents; a Neon "reset from parent" is never used on `preview`. Agents do not run the seed or a migration against a real database themselves, and do not ask for a re-seed: that is the owner's request.

## Row format

Each row is one seeded case. An area slice that adds a seed module adds its rows here in the same change, and the same case, with a check that proves it from the seeded rows, to `SEED_CASES` in [db/seed/cases.ts](../db/seed/cases.ts). A unit test runs every check and fails when this table and that list differ.

| Column | What goes in it |
|---|---|
| Area | The seed module that holds the case, by its `name` in the registry (for example `structure`). |
| Case | The situation in plain words (for example "a closed division with no members"). |
| Data | `public` when the case's rows are the data the site already publishes; `invented` when at least one of its rows is invented, because the public data has no example of the case or the data is private (see [Public and invented data](#public-and-invented-data)). |
| Rows | How to find the rows: table and key (for example `divisions` code `OLD`). |
| Exercised by | The board or issue whose page shows the case, as a link. |

## Connect previews to the preview database branch

This is an owner action. Agents never change a Vercel, Neon or repository setting or an environment variable; the build only documents the setup. The owner finished it on 2026-10-16 (recorded on [#306](https://github.com/PoliTo-Rocket-Team/website-v2/issues/306)), in this shape:

1. **Preview branching is off on the integration.** The Neon integration for Vercel does not create a branch for each preview deployment. The integration cannot choose a parent branch for previews, so it is not used for them. Production reads the Neon `main` branch, with its connection strings set for the **Production** environment only ([ADR 0018](../.decisions/0018-v2-hosting-and-launch.md)).
2. **One schema-only branch named `preview`.** In the Neon console, in the same project, a branch named `preview` was created from `main` with the **Schema only** option. It holds the tables and no rows, so it never holds production data. Its compute endpoint is `ep-floral-mouse-b2er5ebz`, the one Neon endpoint the seed's target check allows.
3. **Preview-only connection strings.** In Vercel, **Project → Settings → Environment Variables**, `DATABASE_URL` (the pooled string) and `DATABASE_URL_UNPOOLED` (the direct string) point at the `preview` branch, with only the **Preview** environment ticked. No production connection string is set for Preview.

The **Development** environment has its own branch, set up by the owner on 2026-10-22 ([ADR 0018](../.decisions/0018-v2-hosting-and-launch.md)): a branch named `development`, copied from `preview`, whose connection strings are set for the Vercel **Development** environment only. So `vercel env pull` brings the `development` branch, never production. The seed's target check refuses the `development` branch, as it refuses every Neon endpoint but `preview`'s, so `pnpm db:seed` from a laptop runs only on a local database.

The target check needs no other variable: it knows the `preview` branch by the endpoint in these two strings, so it needs no Neon API key and no project id (Owner decision on [#311](https://github.com/PoliTo-Rocket-Team/website-v2/issues/311)).

Every preview deployment shares the `preview` branch. Each preview build migrates it, and seeds it only when it is empty, so it holds only the dummy set and the rows testers made on previews, never production rows. A preview's changes last across preview builds (ADR 0016, amendment of 2026-10-21). A seed change merged later reaches the branch only when the branch is empty or the owner asks for a re-seed, below; an ordinary build never re-seeds. A pull request's migration reaches the shared branch before it merges. On a preview with this database, the pages read it, and a check signs in as any seeded person and views as one through real sessions (issues [#612](https://github.com/PoliTo-Rocket-Team/website-v2/issues/612), [#653](https://github.com/PoliTo-Rocket-Team/website-v2/issues/653)). A preview or a `next dev` run with no `DATABASE_URL` stops with a message naming the database it needs, the `preview` branch or the Neon `development` branch ([lib/database-required.ts](../lib/database-required.ts)); there is no in-memory copy of the dashboard to fall back to (issue [#613](https://github.com/PoliTo-Rocket-Team/website-v2/issues/613)).

## Re-seed the preview branch

This is an owner action ([ADR 0016](../.decisions/0016-previews-read-their-own-seeded-branch.md), amendment of 2026-10-24). It empties the shared `preview` branch, test writes and sign-ins included, and loads the dummy set again. Nobody holds a database credential for it: the preview build does it with the Preview connection strings Vercel already gives it.

1. In Vercel, **Project → Settings → Environment Variables**, add `PREVIEW_RESEED_REQUEST` with a value the branch has not served yet, for example today's date `2026-10-25`, and tick only the **Preview** environment. To re-seed again later, change the value (for example `2026-11-02`, or `2026-10-25.2` on the same day). A value is 1 to 64 letters, digits, dots, dashes, colons or underscores; any other value fails the preview build before it connects.
2. Redeploy one preview whose commit carries the re-seed (any preview of `huey/landing-page` from this change on): **Deployments**, open the newest preview, **⋯ → Redeploy**. A variable reaches only builds that start after it is set.
3. In that build's log, the database step reads `emptied it and seeded it again for re-seed request "2026-10-25"`. Every later preview build that carries the same value logs that the request was already served and leaves the rows in place.

The variable may stay set: a served value never re-seeds again. The first build that runs after the variable is set does the re-seed, whichever preview it is (a branch cut before this change ignores the variable), and builds take turns on the lock, so only one does it. It refuses any target but the `preview` branch's endpoint, so a Production value of the variable does nothing: a production build only migrates and ignores it (ADR 0020).
